# 백엔드 계획서 — 웹 · 백엔드 · DB · AI 구조로

> 작성: 2026-11-20 · 상태: **계획 (아직 구현하지 않음)**
> 목표: 상용화할 수 있는 **웹(프론트) → 백엔드 → DB + AI** 구조로 옮기되, 화면은 지금보다 빨라지게 한다.

## 1. 목표 구조

```
            ┌──────────────────────── 서울 리전 ────────────────────────┐
            │                                                             │
 브라우저 ──▶ 웹 (Next.js)  ──HTTPS──▶  백엔드 (FastAPI /v1)  ──SQL──▶  DB (Postgres)
            │   화면만                     업무 규칙·권한·요금제             테이블·RLS
            │                              공개 API·관리자                  Storage(파일)
            │                                   │                             ▲
            │                                   │ 검사 요청 (DB 큐)            │
            │                                   ▼                             │
            │                              AI (Python)  ───────────────────────┘
            │                              · 분석 워커: 컷 분할·얼굴 비교 (오래 걸리는 일)
            │                              · 모델 추론: 캐릭터 구분도 등 (짧은 일)
            └─────────────────────────────────────────────────────────────┘
 로그인: Supabase Auth (토큰 발급) → 웹이 토큰을 백엔드에 전달 → 백엔드가 검증
```

| 계층 | 기술 | 맡는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| **웹** | Next.js 16, TypeScript | 화면, 로그인 화면·세션 쿠키, 백엔드 API 호출 | **DB 직접 접근** (지금의 서버 액션 DB 코드는 모두 백엔드로) |
| **백엔드** | FastAPI, Python 3.12 | 모든 데이터 읽기·쓰기, 업무 규칙, 권한, 사용량·요금제, 업로드 URL 발급, 공개 API, 관리자 | 영상 분석 같은 무거운 계산 |
| **DB** | Supabase Postgres + Storage | 데이터·파일 저장, **RLS(최종 방어선)** | 업무 규칙 |
| **AI** | Python (`pipeline/`, skpipe) | 분석 워커(검사 대기 회차 처리), 모델 추론 | 사용자 요청 직접 받기 |
| **인증** | Supabase Auth | 가입·로그인·토큰 발급 | — |

### 왜 이 구조인가

- **책임이 한곳에:** 요금제·사용량 제한·결제·공개 API·관리자 작업이 모두 백엔드를 지나므로 우회할 수 없다.
- **화면을 바꿔도 API는 그대로:** 앱이나 다른 화면을 붙여도 같은 API를 쓴다.
- **AI 분리:** 영상 분석은 몇 분씩 걸리므로 API 요청과 분리. AI만 GPU 서버로 옮기는 것도 쉬워진다.
- **이중 방어:** 백엔드가 권한을 검사하고, DB의 RLS가 한 번 더 막는다.

## 2. 지금 왜 느린가 (측정, 2026-11-20)

| 측정 | 결과 |
| --- | --- |
| **Supabase 프로젝트 리전** | **ap-southeast-2 (호주 시드니)** |
| 접속 (TCP+TLS, 서울 엣지) | 0.02~0.08초 — 빠름 |
| **요청 하나 처리** (연결 재사용 포함) | **0.43~0.5초** — 서울↔시드니 왕복 때문 |
| 로그인 토큰 서명 | ES256 (비대칭) — 인증 서버 왕복 없이 로컬 검증 가능 |

페이지마다 이 요청을 차례로 기다린다:

| 페이지 | 차례로 기다리는 요청 | 예상 대기 |
| --- | --- | --- |
| 메인 (시리즈 목록) | 1 | 약 0.5초 |
| 시리즈 상세 (회차·캐릭터·장소 탭) | 3 | 약 1.4초 |
| 검수 리포트 | 5 | 약 2.3초 |

그 밖에: 개발 모드(`npm run dev`)는 페이지마다 그 자리에서 컴파일하고, 로딩 화면(`loading.tsx`)이 없어 클릭 후 멈춘 것처럼 보인다.

**결론:** 느린 주원인은 **DB가 시드니에 있는 것**이다. 백엔드를 추가하면 거쳐 가는 곳이 하나 늘기 때문에, **서울로 옮기는 게 백엔드 도입의 전제 조건**이다.

### 백엔드를 거쳐도 빨라지는 이유

```
지금:   웹 서버 ──(Supabase REST, 시드니 왕복 0.45초)× 3~5번──▶ DB      ≈ 1.4~2.3초
목표:   웹 서버 ──(서울 안 0.01~0.03초)──▶ 백엔드 ──(같은 리전 SQL, 수 ms)× N──▶ DB  ≈ 0.1~0.2초
```

백엔드가 DB에 **같은 리전에서 직접 SQL로** 붙고, 한 API가 필요한 데이터를 한 번에 모아 돌려주면 웹은 **페이지당 API 1~2번**만 기다린다.

## 3. 0단계 — Supabase를 서울로 옮기기 (가장 먼저, 반나절)

> **완료 (2026-11-20).** 새 프로젝트(서울)에 마이그레이션 8개 적용, `web/.env`·`pipeline/.env` 교체.
> 같은 측정에서 요청 하나가 0.43~0.5초 → **0.02~0.07초**(연결 재사용 기준)로 줄었다. 테이블·버킷·로그인 토큰(ES256) 확인.

지금 데이터는 테스트용이고 DB 구조는 `supabase/migrations/`에 모두 있어서 옮기기 쉽다.

1. Supabase에서 **새 프로젝트**를 **Northeast Asia (Seoul) `ap-northeast-2`** 에 만든다.
2. SQL Editor에서 `supabase/migrations/`의 파일을 **이름 순서대로** 한 번씩 실행한다 (현재 8개).
3. 새 프로젝트의 **Authentication → URL Configuration**에 Site URL·Redirect URL을 다시 넣는다.
4. 키 교체: `web/.env`(URL·Publishable key), `pipeline/.env`(URL·Secret key).
5. 회원가입·시리즈·캐릭터 사진·회차를 다시 만들어 동작 확인. (계정은 옮겨지지 않으므로 다시 가입)
6. 측정: 요청 하나 0.45초 → 목표 0.05초 안팎.
7. 문제가 없으면 시드니 프로젝트를 삭제한다 (무료 플랜 프로젝트 수 제한).

## 4. 1단계 — 화면 속도 기본기 (구조와 상관없이, 2~3일)

| 할 일 | 효과 |
| --- | --- |
| 속도는 **빌드한 상태**(`npm run build` → `npm start`)로 잰다 | 개발 모드 컴파일 시간 제외 |
| 시리즈·리포트 경로에 **로딩 화면** (`loading.tsx`, 뼈대 화면) | 클릭 즉시 반응 |

| 차례로 기다리던 조회를 `Promise.all`로 동시에 (백엔드로 옮기기 전까지 임시) | 대기 횟수 감소 |

**목표:** 빌드 상태에서 페이지 이동 0.5초 이내 (중간값).

## 5. 백엔드(FastAPI) 설계

### 5.1 인증과 권한

- 로그인은 지금처럼 **Supabase Auth**. 웹이 받은 토큰(JWT)을 `Authorization: Bearer`로 백엔드에 보낸다.
- 백엔드는 Supabase 공개 키(**JWKS, ES256**)로 토큰을 **직접 검증**한다 (키는 캐시, 인증 서버 왕복 없음).
- **RLS를 살린 DB 접근:** 요청마다 트랜잭션을 열고
  `set local role authenticated` + `set_config('request.jwt.claims', <검증한 토큰 내용>, true)`
  를 설정한 뒤 쿼리한다. 그러면 지금의 `auth.uid()` RLS 정책이 그대로 적용된다 — **백엔드에 실수가 있어도 남의 데이터는 DB가 막는다.**
- 관리자 키(service role)는 관리자 API와 AI 워커에만. 웹에는 두지 않는다.
- 외부 연동용 **API 키**: DB에는 해시만 저장, 권한 범위·만료일 지정.

### 5.2 DB 연결

- PostgREST(REST)를 거치지 않고 **Postgres에 직접** (Supavisor 풀러 transaction 모드, `asyncpg`).
- 스키마 기준은 그대로 `supabase/migrations/`. 백엔드 코드가 테이블을 따로 만들지 않는다.

### 5.3 파일 업로드

큰 파일은 백엔드를 거치지 않는다:
1. 웹 → 백엔드: "업로드하고 싶다" → 백엔드가 권한·용량·요금제를 확인하고 **서명된 업로드 URL** 발급
2. 브라우저 → Storage: 그 URL로 직접 업로드 (지금처럼 진행률 표시)
3. 웹 → 백엔드: "다 올렸다" → 백엔드가 확인하고 DB에 기록

### 5.4 API (초안, `/v1`)

| 메서드·경로 | 하는 일 |
| --- | --- |
| `GET /v1/health` | 상태 확인 |
| `GET /v1/me` | 내 정보·요금제·이번 달 사용량 |
| `GET/POST /v1/series`, `GET/PATCH/DELETE /v1/series/{id}` | 시리즈 |
| `GET /v1/series/{id}/overview` | **상세 화면 한 번에**: 시리즈 + 탭 데이터 + 파일 URL (요청 1번) |
| `POST /v1/series/{id}/characters`, `PATCH/DELETE /v1/characters/{id}` | 캐릭터 |
| `POST /v1/characters/{id}/references/upload-url`, `PUT /v1/characters/{id}/references/{angle}`, `DELETE …` | 레퍼런스 이미지 |
| (장소도 같은 모양) | 장소·장소 이미지 |
| `POST /v1/series/{id}/episodes/upload-url`, `POST /v1/series/{id}/episodes`, `DELETE /v1/episodes/{id}` | 회차 영상 |
| `POST /v1/episodes/{id}/check` | 검사 요청 (여기서 사용량 한도 확인) |
| `GET /v1/episodes/{id}/report` | **검수 리포트 한 번에**: 회차·이슈·레퍼런스·URL (요청 1번) |
| `PATCH /v1/issues/{id}` | 검토 상태 (해결됨·오탐) |
| `POST /v1/characters/distinctness` | 캐릭터 구분도 경고 (AI 모델 추론) |

- 화면 하나에 필요한 데이터는 **API 하나가 모아서** 돌려준다 (요청 횟수 최소화).
- 오류 형식 통일 (RFC 9457 `application/problem+json`), 목록은 커서 기반 페이지.
- 다시 보낼 수 있는 요청(업로드 확인 등)은 `Idempotency-Key`로 중복 방지.
- OpenAPI 문서(`/docs`) 자동 생성 → 웹의 TypeScript 타입도 여기서 생성.

### 5.5 상용화 기능

- **사용량:** 사용자별 월 분석 분(分) 기록. 검사 요청 때 한도 확인, 분석 완료 때 확정.
- **요청 제한:** 사용자·API 키별 분당 요청 수 (처음엔 Postgres, 커지면 Redis).
- **결제:** PG사 웹훅 수신·서명 검증·요금제 반영 (결제사는 상용화 단계에 결정).
- **감사 기록:** 관리자 작업·요금제 변경을 별도 테이블에.

## 6. AI 계층

| 구성 | 하는 일 | 백엔드와의 연결 |
| --- | --- | --- |
| **분석 워커** (지금 있음, `skpipe worker`) | 검사 대기 회차를 가져와 컷 분할·얼굴 비교·이슈 저장 | **DB 큐**: 백엔드가 회차를 "검사 대기"로 바꾸면 워커가 `claim_next_episode()`로 가져간다 |
| **모델 추론** (새로) | 캐릭터 구분도처럼 몇 초 안에 끝나는 계산 | 처음엔 백엔드 안에서 `skpipe`를 불러 쓰고, 무거워지면 내부 전용 AI 서비스로 분리 |

- AI 코드는 지금처럼 `pipeline/`(skpipe)에 두고, 백엔드와 워커가 같은 패키지를 쓴다.
- 모델(DINOv2 등)은 메모리를 많이 써서, 트래픽이 커지면 **AI만 따로** 키우거나 GPU 서버로 옮긴다.

## 7. 폴더·운영

```
series-keeper/
  web/        웹 (Next.js) — 화면만
  api/        백엔드 (FastAPI)   ← 새로
  pipeline/   AI (skpipe: 분석 워커·모델)
  supabase/   DB 스키마 (마이그레이션)
```

| 항목 | 계획 |
| --- | --- |
| 테스트 | pytest + httpx. DB 테스트는 로컬 Supabase(`supabase start`, Docker)로 RLS까지 확인 |
| CI | `api.yml` 추가 (린트·타입·테스트) |
| 배포 | 웹: Vercel 서울(`icn1`) / 백엔드·AI: Docker, 서울(예: Cloud Run `asia-northeast3`) / DB: Supabase 서울 — **모두 같은 리전** |
| 비밀 값 | 배포 환경 변수로만. 관리자 키는 백엔드·AI에만 |
| 관측 | 요청 ID가 붙은 구조화 로그, 오류 추적(Sentry 등), API별 응답 시간 |

## 8. 단계별 일정

| 단계 | 기간 | 내용 | 끝났다고 보는 기준 |
| --- | --- | --- | --- |
| 0. 리전 이전 | 반나절 | 3장 | 요청 하나 0.1초 미만 |
| 1. 속도 기본기 | 2~3일 | 4장 | 빌드 상태 페이지 이동 0.5초 이내 |
| 2. 백엔드 뼈대 | 약 1주 | `api/`, JWT 검증, RLS 살린 DB 접근, `/v1/health`·`/v1/me`·`GET /v1/series`, 테스트·CI·Docker | 다른 사람 토큰으로는 내 시리즈가 안 보이는 테스트 통과 |
| 3. 읽기 이전 | 약 1주 | 메인·상세·리포트 화면이 `overview`·`report` API로 | 웹 코드에 Supabase 데이터 조회가 남지 않음, 페이지당 API 1~2번 |
| 4. 쓰기 이전 | 1~2주 | 시리즈·캐릭터·장소·회차·검사 요청·검토를 API로, 업로드 URL 방식 | 서버 액션에 DB 코드가 남지 않음 (웹은 화면만) |
| 5. 상용 기능 | 2주~ | 사용량·요금제 한도, API 키·공개 문서, 관리자 API, 캐릭터 구분도 | 무료 한도를 넘으면 검사 요청이 막힘 |
| 6. 배포 | 1주 | 서울 리전 배포, 모니터링, 워커 서버 | 외부에서 가입~검사~리포트까지 동작 |

## 9. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 거쳐 가는 곳이 늘어 느려짐 | 0단계(서울 이전)를 먼저. 모든 계층 같은 리전. 화면당 API 1~2번이 되도록 API를 화면 단위로 설계. 단계마다 응답 시간 측정 |
| 옮기는 동안 로직이 웹·백엔드 두 곳에 | 화면(기능) 단위로 한 번에 옮기고, 옮긴 서버 액션은 바로 지운다 |
| 운영할 서버가 늘어 비용 증가 | 2~5단계는 로컬·무료 플랜. 배포는 상용화 직전에 |
| 권한 실수 | 백엔드 검사 + DB RLS 이중 방어. 관리자 키는 관리자 API·AI 전용 |
| AI 모델이 백엔드 메모리를 많이 씀 | 모델 추론은 필요해지면 별도 AI 서비스로 분리 |
